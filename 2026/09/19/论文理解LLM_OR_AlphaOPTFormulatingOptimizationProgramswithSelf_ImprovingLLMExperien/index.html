  • 摘要：优化建模是各行业关键决策制定的基础，但其自动化实施仍具挑战性：自然语言问题描述必须转化为精确的数学形式化表达和可执行的求解器代码。现有基于 LLM 的方法通常依赖脆弱的提示或成本高昂的重新训练，两者的泛化能力都有限。近期研究表明，大模型可以通过复用经验获得改进，但如何在结构约束严格的场景下系统地获取、精炼和复用这些经验仍不清楚。我们提出 AlphaOPT，一个能够让 LLM 从有限监督中学习优化建模知识的自我改进经验库，包括在没有标准程序、标注推理轨迹或参数更新的情况下，仅利用答案反馈进行学习。AlphaOPT 通过两个阶段持续循环运行：Library Learning 阶段从失败尝试中提取经求解器验证的结构化经验；Library Evolution 阶段根据跨任务聚合的证据，精炼已存经验的适用性。这种设计使模型能够积累可复用的建模原则，改善跨问题实例的迁移，并使经验库的增长随时间保持有界。在多个优化基准上的评估表明，随着更多训练数据可用，AlphaOPT 持续改善表现（训练样本从 100 条增加到 300 条时，准确率从 65% 提高到 72%），并在两个分布外数据集上分别超过最强基线 9.1% 和 8.2%。这些结果表明，以求解器反馈为依据的结构化经验学习，为需要精确形式化表达与执行的复杂推理任务提供了重新训练之外的一种实用选择。

1. 背景与动机

1.1 研究背景

  • 本文研究优化问题的\自动建模与编程，以减轻对人类专家的严重依赖。具体而言，这类问题要求输入一段自然语言描述的问题（如配送货、生产规划等问题），要求模型或系统完成运筹学建模，并生成问题求解代码，中间常需要显式写出数学公式
  • 针对该任务，当前主要存在基于提示和基于微调的两类方法：
    1. 基于提示的建模prompt-based modeling：通过为 GPT-4o 等大规模预训练 LLM 精心设计建模 Prompt 来工作，相关方法包括 OptiTree、PaMOP、OptiMUS 等。这类方法的重点在于通过引入树、图、多智能体等设计，将 “复杂问题描述上下文 -> 严格式要求代码” 的端到端生成过程拆分为多个子过程，从而降低各环节难度，并使各环节的 prompt 更具针对性和指向性

      这类方法的优势是不改模型参数，工程上容易迭代；弱点是很依赖基础模型本身的优化建模知识，复杂长题中容易漏约束或变量类型，且对细微的措辞变化和领域偏移敏感

    2. 基于微调的建模fine-tuned LLM modeling agents：通过构造大规模运筹学及建模知识对 LLM 进行微调，形成专用的建模语言模型，如 ORLM、Step-Opt 等。这类方法的重点在于设计数据构方法和错误过滤方法，实现多样、正确、难度可控的高质量数据集。此外，从 2025 年开始也逐步出现了基于 RL post-training 的方法，如 SIRL 将 OR 建模求解视作 RLVR 任务解决、LLMOPT 使用在 sft 后使用 KTO 后训练减弱模型幻觉等

      通过进行针对性训练，基于微调的方法往往可以用更小参数量的模型达成和通用大模型相似的性能，但问题在于真实高质量优化建模样本少，人工标注贵，简单数据又无法覆盖长上下文、复杂约束和跨领域表达，且当前学术界中的大多数数据集仅提供解决方案，而非指导建模决策的中间推理过程，这限制了微调方法的泛化能力

1.2 动机

  • 作者注意到：在信息检索和网页浏览等任务中，大型模型可通过复用经验（即存储反思记录、推理依据或代码编辑，并将其应用于新任务）提升性能。作者将优化建模与通用经验学习两条线连接起来
    路线 典型工作 流程 AlphaOPT 关注的不足
    提示与智能体编排 OptiMUS、ORThought、Chain-of-Experts 通过分步推理、角色分工和工具反馈生成模型 固定流程本身不会自动积累新的适用规则
    领域后训练 ORLM、LLMOPT 把建模数据中的模式学入模型参数 需要训练与标注，新增知识不易直接检查和修改
    结构化知识检索 CIR、LEAN-LLM-OPT、OptiTree 用领域模板、案例或中间表示辅助当前任务 还需要解释知识如何从错误中获得、如何修正适用边界
    反思与经验复用 Reflexion、ExpeL 保存失败后的反思，从轨迹中提炼可迁移经验 经验多为 “检查变量类型”、“考察边界情况” 等高层提醒，缺少具体结构、触发条件和可执行例子
  • 把 Reflexion 等通用经验学习方法直接平移到 LLM-OR 任务上存在三方面困难
    1. 经验适用性差：经验大多以自由格式的文本或代码形式存在，并依赖基于 embedding 的相似性索引或粗略的 meta data 来索引，缺乏明确且可验证的前置条件（如适用场合、不适用场合、需满足的前提等），这可能在分布偏移时增加经验索引失效风险，并误导建模方向
    2. 验证机制不完善：模型生成的经验缺乏验证机制，或验证范围仅限于任务级结果（如任务达成），不能保证底层知识在结构上是有效或可迁移的
    3. 经验组织低效：经验往往被组织成一个扁平的项目列表，而运筹学则涉及不同建模阶段和问题类型中多样化的见解，因此本质上需要对所获取的知识进行更高效的组织
  • 规则内容有用，并不意味着它对所有看起来类似的问题都适用，下图给出一个案例：模型曾经漏写了 “卡车必须回仓库” 的约束，于是学到一条纠错经验；后来又发现，并非所有运输问题都要求回仓库，所以要给这条经验加上适用条件
    1. 左侧在一个配送任务中发现错误：任务要求卡车给多个客户配送，并求最短总行驶距离，LLM 生成的代码只约束卡车从仓库出发，却没有约束它回到仓库，因此和参考答案不匹配
    2. 中间把具体错误提炼成可复用经验：LLM 整理得到错误经验 “如果任务要求车辆从仓库出发并返回仓库，建模时就不能只约束出发，还要显式约束返回” 。AlphaOPT 使用分类树组织不同粒度建模知识，这个教训放入 “领域建模 → 路径规划 → 流量守恒” 的分类下，并保存：
      • 适用条件：什么问题需要这条经验。
      • 解释：为什么需要补充这些约束。
      • 示例：错误代码和修改后的代码。
    3. 右边用其他任务检查这条经验是否用得合适：这里给了两个例子，第二种情况（允许车辆在客户处过夜，路线跨越多天）不能直接照搬 “当日必须回仓库” 的约束，机械套用经验会添加题目没有要求的限制，排除本来合法的路线。因此经验的适用条件被修正为： 当任务明确要求闭合路线、返回同一仓库时，检查并补全相应约束；对于开放路线或允许跨日停留的任务，先确认其终点和返回要求。

2. 本文方法

  • 从头训练时，AlphaOPT 在训练集上进行指定轮数的迭代，无早停设计
    • 第 1 轮只进行经验学习（左侧框黑线）：逐一求解训练任务，从失败与修正中提取经验，建立初始经验库及分类树
    • 从第 2 轮开始，先诊断（左侧框红线），再精炼（右侧框）：使用已有经验库重新求解任务，记录经验误用、漏检索等证据，必要时补充新经验；本轮诊断阶段全部完成后，再按经验汇总关联任务证据，统一进入精炼阶段，更新经验条件

2.1 经验的表示、组织与索引

2.1.1 经验表示

  • 作者将经验定义为结构化的四元组形式

    Ii=(τi,ci,ei,xi).I_i=(\tau_i,c_i,e_i,x_i). Ii​=(τi​,ci​,ei​,xi​).

    • τi\tau_iτi​ ：分类（Taxonomy），用于分类和粗检索；
    • cic_ici​ ：条件（condition），描述前提、触发信号和排除条件；
    • eie_iei​：解释（explanation），解释正确原则、常见错误及原因；
    • xix_ixi​：示例（example） ，用数学表达或代码对照错误与正确写法。

  • Condition 决定是否调用，Explanation 和 Example 决定如何使用。

    • 例如要求一个仓库只有启用后才能发货，每天最多发 100 件。 用 y∈{0,1}y\in\{0,1\}y∈{0,1} 表示是否启用仓库，用 f≥0f\ge0f≥0 表示当天发货量。如果模型只写 f≤100f\le100f≤100，就可能允许导致未启用仓库发货，正确写法应为 0≤f≤100y.0\le f\le100y.0≤f≤100y.

    • 这次纠错可以整理为一条经验 "业务量应当与启用状态关联起来"，对应的四元组为：

      字段 这个例子中保存的内容
      分类 通用建模 → 约束建模 → 启用状态与业务量的关联约束
      条件 题目明确要求 “只有启用后才能开展业务”，且业务量有已知的有效上界
      解释 只限制业务量上限还不够，必须把业务量与启用状态关联起来，避免未启用时仍有业务量
      示例 错误：只写 f≤100f\le100f≤100；修正：结合 f≥0f\ge0f≥0 和二元变量 yyy，写成 f≤100yf\le100yf≤100y

2.1.2 经验组织

  • AlphaOPT 用可扩展的分类树组织经验，其使用 “预设框架＋模型动态扩展” 设计，包含预定义的三条主线和三层结构，具体标签可随经验积累而扩展。如下表所示

    结构 是否固定
    三条主线：Domain Modeling（领域建模）、General Formulation（通用数学建模）、Code Implementation（代码实现） 预先设定
    每条主线下采用 Level-1 → Level-2 两级标签 预先设定
    具体标签的名称和数量 从少量初始标签出发，LLM 按需扩展
    标签的适用条件（condition） 由 LLM 编写

  • AlphaOPT 在训练任务上逐步积累经验后形成了 14 个一级标签和 38 个二级标签

  • 分类树是整个库的公共目录，四元组的 taxonomy 表示一条经验在目录中的分类路径。构造新经验时，prompt 给出任务和纠错材料 + 当前阶段的分类树分支

    • 数学建模阶段：传入 Domain Modeling 和 General Formulation 两条主线下的完整分类字典
    • 代码生成阶段：传入 Code Implementation 下的完整分类字典

  • 生成经验 taxonomy 时要求选择一个主线、一个 Level-1 和一个 Level-2 标签。输出时允许扩展新增 Level-1 和 Level-2 标签，但不能加层数或主线。有以下三种情况

    情况 模型输出与程序处理
    已有完整路径适用 复用 Level-1 和 Level-2；生成格式中的叶节点值为 null
    一级类别合适，但缺少具体标签 在已有 Level-1 下新增 Level-2 叶节点
    已有一级类别都不合适 新增 Level-1，并在其下创建 Level-2

    注意标签条件与经验条件作用不同：新标签的 condition 随分类信息保存在公共分类字典中，用于描述该类知识何时相关；四元组中独立的 condition 属于具体经验，用于后续逐条检查。两者都叫 condition，但不能混为同一个字段

    • 编码经验提取提示 PROMPT_INS_FROM_PROGRAM

2.2.3 若需提取建模经验，先获得参考程序

2.4 经验精炼（Library Refinement）

  • 经验精炼在本轮诊断完成后执行，它逐一检查经验，会先找关联的失败问题，然后一次性提出若干修订 condition 候选，最后在关联问题上重新检索，找到最优修订条件，经验四元组中除 condition 以外的部分保持不变

  • 如下图所示，一条经验可能有三种索引情况，关联任务索引到正确经验（positive）、关联任务索引到错误经验（negative）和正确经验未被关联任务召回（unretrieved）

    • positive → keep：原来用对的任务，修改后仍应召回这条经验。
    • negative → remove：原来误用的任务，修改后应排除这条经验。
    • unretrieved → add：原来漏掉、但其实需要它的任务，修改后应召回。

    模型据此生成几个新版条件，再在关联任务上重新跑检索，比较哪个版本更符合上述要求，选出更好的版本写回经验库

    下图示意了经验精炼如何将一条经验的 condition 从 “只覆盖最初的任务” 改成 “能覆盖更多适用任务，同时排除不适用任务”

    • 绿色点：这条经验适用、能提供帮助的任务；
    • 蓝色点：这条经验本来也有用，但原条件没有让它被召回的任务
    • 红色点：不适合使用这条经验、使用后可能被误导的任务
    • 灰色虚线小圈是初始条件。 它只圈住绿色任务，表示条件写得太局限：原任务能用，其他同样需要这条经验的蓝色任务却被漏掉
    • 黑色曲线是精炼后的边界，右侧绿色区域表示适用范围。 新条件既保留绿色任务，也覆盖两个蓝色任务，同时把红色任务留在适用范围外
    • 箭头表示重写 condition 得到新条件，让 LLM 更准确地判断哪些任务需要这条经验

2.4.1 选择待精炼经验，整理关联任务

2.4.6 优化视角与收敛论证的适用范围

  • 原文 §3.3 用一个带库复杂度惩罚的目标解释整个过程：

    max⁡ℓ∈LEt∼T[Success⁡(t∣ℓ)]−λΩ(ℓ).\max_{\ell\in\mathcal L} \mathbb E_{t\sim\mathcal T}[\operatorname{Success}(t\mid\ell)] -\lambda\Omega(\ell). ℓ∈Lmax​Et∼T​[Success(t∣ℓ)]−λΩ(ℓ).

    其中 ℓ\ellℓ 是一个候选经验库，L\mathcal LL 是库空间；Success 表示能否得到参考最优目标值；Ω\OmegaΩ 衡量经验条数或冗余等复杂度。直觉是增加可复用的成功经验、压缩重复知识，而不是无限追加上下文
  • 附录 A 的有限空间论证假设说明：在理想假设下，经验库不能无限改进，并且最终找不到允许范围内的更好修改。 这里把整个经验库的一个版本视为一个状态，用上面的目标 F(ℓ)F(\ell)F(ℓ) 评价它：既考虑任务收益，也扣除库复杂度。有限空间论证可以分成三步理解：
    1. 为什么不能无限改进？ 假设可能的经验库版本只有有限种，每次接受修改都让 F(ℓ)F(\ell)F(ℓ) 严格提高。这样就不可能回到旧版本，因为旧版本的分数更低；有限种版本只能支持有限次严格改进。这里的“有限”指可能的库版本数量有限，仅仅一份库中的经验条数有限还不够。
    2. 为什么能称为局部最优？ 还需要假设：只要允许的修改中存在更好的版本，系统最终就能找到并采用它。因此，改进结束时，在这些允许的修改范围内已没有更好的版本，这才叫局部最优。它不意味着找到了所有可能经验库中的全局最优。
    3. 为什么论文还要求训练、测试分布相同？ 这个假设用于让训练目标与测试目标一致，从而把训练目标上的局部最优结论用于测试目标；它不是“有限版本无法无限改进”这一步的必要理由。附录还讨论了无限库空间，在目标有界的基础上加入空间紧致、目标连续等假设，给出目标值收敛及极限点性质的论证。
  • 这是一套带前提的理论解释，不能直接当作实际代码的性能保证。 真实系统每轮只生成有限个候选，可能漏掉更好的修改；精炼提高的是检索评分，也不保证整个库的任务收益减复杂度这一目标同步提高。代码按指定轮数结束，并未检查是否已经达到局部最优。因此，这段论证有助于理解“持续接受更好的修改”为什么可能趋于稳定，但不能证明当前实现一定达到局部最优，也不能证明训练与测试分布不同的 OOD 任务上仍有同样结论；主文将其定位为概念性论证（conceptual sketch）

  • 实验设定：在四个 Test Split 与两个 OOD 集合上，比较三类基线与 AlphaOPT 的目标值匹配准确率，主结果及消融结果如下

    2. 不是每个单列都独胜：NL4OPT 上 ORLM 为 87.5%，高于 AlphaOPT 的 81.2%；IndustryOR 上 AlphaOPT 与 ORThought 均为 60.0%。
    3. OOD 的 LogiOR 为 56.0%，比 ExpeL 的 47.8% 高 8.2 个百分点；OptiBench 为 93.5%，比 ORThought 的 84.4% 高 9.1 个百分点
    4. OOD Micro/Macro 为 86.5%/74.8%。两者差距说明容易且较大的 OptiBench 拉高了加权成绩；LogiOR 仍有约 44% 的任务失败。

3.2.6 学到的知识集中在哪里

  • 实验设定：按经验的二级标签与来源数据集统计分布，原文 Figure 7 的三个面板分别对应 Domain Modeling、General Formulation 和 Code Implementation

  • 领域建模经验分布如下：

    1. 容量/资源平衡条目最多，并且来自四个数据集；这类错误不是单一数据集特有的措辞问题。
    2. 流守恒与最大流目标也较集中，表明 LLM 容易遗漏局部守恒与整体网络结构之间的关系。
    3. 较小的 IndustryOR、MAMO 也贡献大量经验，说明样本数不是经验价值的唯一指标，结构复杂性同样重要。

  • 通用形式化经验分布如下：

    1. 显式变量界、冗余辅助变量、连续/离散混淆位于前列；基础变量定义足以决定可行域是否正确。
    2. 单位不一致、关系运算符错误等问题跨数据集出现，适合提炼成可复用的检查规则。
    3. 经验数量衡量被系统提取并保存的知识，受抽取、合并与验证影响，不能无条件等同于原始错误频次。

  • 实现类经验分布如下：

    1. 非线性约束处理、键与索引不匹配较突出，前者连接建模变换与 API 能力，后者连接模型索引与实际数据。
    2. 严格不等式与求和语法是相对局部、容易用示例落实的规则；它们更适合短经验辅助。
    3. 即使总比例只有 18%，实现错误仍可能使完整模型无法运行，不能只优化自然语言到公式的前半程。

3.2.7 检索成功后，经验真的被正确使用了吗

  • 实验设定：在全部评估集合上比较有库与无库的结果，排除两种设置都成功的任务，再将所分析的经验作用分类为 success、failure、invalid

    1. Success 为 128，48.3%：经验帮助避免原本会出现的错误；Failure 为 45，17.0%：误匹配或误用引入新错误。
    2. Invalid 为 92，34.7%：经验匹配正确但没有修复原错误。把这些情况当作“检索成功，因此任务成功”会显著高估系统。

  • 分类别观察，更能区分“条件错”与“执行错”：

    1. Solver & API Syntax 为 48 次成功、17 次无效，局部语法知识更容易落实；Variable Definition 有 45 次成功，也有 20 次失败，变量界过强仍会损害建模。
    2. Facility Location 中图示 7 次失败、1 次成功、2 次无效，与正文讨论的 70% 失败比例一致，主要风险是把启用逻辑强加给没有该语义的问题。
    3. Resource Allocation 的无效数量为 29，Production Planning 为 11，反映系统即便识别了知识，也未必能完成跨阶段、跨资源的完整约束组合。

  • 附录举出 “严格不等式改写为差 1 的非严格不等式” 的实现经验。这里必须补充适用前提：若 x,yx,yx,y 为整数，x<yx<yx<y 等价于 x≤y−1x\le y-1x≤y−1；对一般连续变量并不成立。这正好说明，经验条目需要明确变量域与精度，不能把局部技巧当成普遍数学规则

  • 作者在主文脚注报告，自探索程序与参考解核查中发现 3 个伪通过案例，约 0.8%，主要为不影响数值结果的变量类型不精确。这个审计缓解了对当前样本的担忧，但不能证明目标值验证在任意新任务上都可靠；多实例回放与一致性检查仍被列为后续工作。

4. 总结

4.1 创新思想来源

  • 从论文直接引用的 Reflexion、ExpeL、规则学习和持续记忆研究来看，AlphaOPT 延续了“把交互反馈变成可复用知识”的路线。它比较鲜明的贡献，是把优化建模的经验定义成具有适用语义、具体示例和回放验证的规则，并将条件精炼变成由关联任务聚合证据驱动的步骤。
  • 我觉得最值得借鉴的不是智能体数量，而是对失败原因的划分：缺知识、知识没被找到、找到但用错、找到却没执行到位。它们分别需要补充内容、修检索条件、增加排除条件、改进解释与实现示例。把这些问题都交给“再反思一次”，通常会失去针对性。

4.3 未来展望

  • 把单实例验证扩展为结构保持的多实例验证。 对数值参数做合理扰动，再核查约束、可行性与目标值，能更有效地识别遗漏约束却碰巧答案一致的模型。还应区分参考标签错误与生成模型错误，防止错标签污染经验库。
  • 把自然语言 condition 接到显式结构上。 例如记录“变量为整数”“存在二元启用逻辑”“只有一个汇点”等可检查前提，并与 CIR/R2C 一类规则表示结合。这是笔记作者提出的组合方向，尚不是本文已验证的结果。
  • 让检索得分更接近最终任务效用。 对收益最大的候选或高风险规则增加完整程序回放；把负迁移的代价、历史任务退化和多条经验冲突纳入筛选，避免只提高平均检索得分。
  • 加强知识落地与规模验证。 当前 invalid 比例提示，经验解释与示例还需要更好地支持实例化；工业场景还需要验证求解时间、模型规模、长期漂移和调用成本。库规模稳定只解决一部分可扩展性问题。

4.4 Q&A

Q1：有参考最优值了，为什么还要生成程序？ A：参考值用于训练阶段判断探索是否成功；最终目的是把经验迁移到没有答案的新任务。单独记住一个数值不会提供变量、约束或可复用的建模规律，生成程序则提供可执行的经验锚点。

Q2：这是否就是 RAG？ A：推理时确实包含检索增强，但检索库是从任务失败中学出来、经回放筛选并持续修改适用条件的。区别主要在知识获取和维护机制，不能只从“有没有检索”判断贡献。

Q3：为什么条件更新不用把所有候选都完整求解一遍？ A：检索重放更便宜，且直接针对过宽、过窄这类错误；代价是它只优化代理指标。如果经验被找到了却无法正确执行，检索得分上升未必带来答案正确率提升。

Q4：经验库会稳定，是不是就保证泛化？ A：不保证。稳定可能来自当前训练集的知识饱和，也可能来自检索或探索瓶颈。附录理论假设训练测试同分布，而 OOD 能力必须由独立实验验证；当前 LogiOR 的 56.0% 仍显示明显局限。
